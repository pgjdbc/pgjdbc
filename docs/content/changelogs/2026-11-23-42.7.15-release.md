title:  PostgreSQL JDBC Driver 42.7.15 Released
date:   2026-11-23 09:01:00 -0500
categories:
    - new release
version: 42.7.15
summary: "Security release: fixes 14 advisories, 8 with a CVE (CVE-2026-134841 to CVE-2026-134848). Fixes SQL injection through the query parser, simple query mode and a half-written Bind, catalog queries that ran other roles' operators, TLS settings that were not enforced, GSS packet replay, a NUL in startup parameters and a BigDecimal stored as a different number. An ssl value other than true, false or empty is now refused when sslmode is not set."

**Notable changes**

### Security
* fix: a `}` inside a string literal, quoted identifier, dollar quote or comment no longer ends a `{d}`, `{t}`, `{ts}`, `{oj}` or `{escape}` JDBC escape, or the text after the arguments of a `{fn}` escape. Before, the rest of the literal was parsed as SQL and `{fn}` escapes in it were translated, so quoted text inside such an escape could run as SQL even with its quotes doubled. An unterminated literal inside an escape now fails in the driver, as it does outside of one. This affects all versions through 42.7.14 [GHSA-4743-5rfh-f7mp](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-4743-5rfh-f7mp) [CVE-2026-134841](https://nvd.nist.gov/vuln/detail/CVE-2026-134841)
* fix: the parser now accepts the same identifier and dollar quote tag characters as the backend: every non-ASCII character, including symbols such as `U+00A7`, non-ASCII spaces and characters outside the BMP. Before, the driver did not see a dollar quote whose tag had such a character and read the quoted text as SQL: a `?` became a placeholder, a `;` split the statement, and JDBC escape processing could create a closing tag that was not in the original text. A surrogate without its other half is the exception: the driver sends it as `?`, an operator character for the backend, so `$$` after it starts a dollar quote. This affects all versions through 42.7.14 [GHSA-4743-5rfh-f7mp](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-4743-5rfh-f7mp) [CVE-2026-134841](https://nvd.nist.gov/vuln/detail/CVE-2026-134841)
* fix: an `E''` string with a doubled quote or a continuation on a new line is now scanned as one escape string. Before, the driver read the part after `''` as a standard string, so `\'` ended the string for the driver but not for the backend. Text in the literal was then treated as SQL, and with `preferQueryMode=simple` a parameter value could run as SQL. `E''` after a vertical tab, which PostgreSQL 17 and later count as whitespace, or after an unpaired surrogate is now also scanned as an escape string. This affects all versions through 42.7.14 [GHSA-4743-5rfh-f7mp](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-4743-5rfh-f7mp) [CVE-2026-134841](https://nvd.nist.gov/vuln/detail/CVE-2026-134841)
* fix: `{fn right(a, b)}` and `{fn timestampdiff(t, b, c)}` now put the subtracted argument in parentheses. Before, an argument that started with a minus sign made `--`, which commented out the rest of the line, so text after the next newline, even inside a string literal, could run as SQL. The parentheses also fix the result of an expression such as `{fn right(a, 1+1)}`. The deprecated `EscapedFunctions` class gets the same change. This affects all versions through 42.7.14 [GHSA-4743-5rfh-f7mp](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-4743-5rfh-f7mp) [CVE-2026-134841](https://nvd.nist.gov/vuln/detail/CVE-2026-134841)
* fix: with `preferQueryMode=simple`, a string parameter with a backslash is now sent as an `E''` literal, which the backend reads the same way whatever `standard_conforming_strings` is. Before, the driver escaped the value for the last setting it knew of. When an earlier statement of a multi-statement query or batch, a trigger or a configuration reload turned the setting off, a value that started with `\'` ended the literal and the rest of it ran as SQL. This affects all versions through 42.7.14 [GHSA-6rxc-3r4p-gpff](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-6rxc-3r4p-gpff) [CVE-2026-134842](https://nvd.nist.gov/vuln/detail/CVE-2026-134842)
* fix: a query parsed while `standard_conforming_strings` had one value is no longer reused from the statement cache after it changes. In simple mode, a statement with a parameter and a backslash that was prepared before the change now fails with SQLState `55000` when it is executed after it. Before, a query such as `SELECT ?, '\', ?` kept the placeholders of the old parse, and the second value ran as SQL. This affects all versions through 42.7.14 [GHSA-6rxc-3r4p-gpff](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-6rxc-3r4p-gpff) [CVE-2026-134842](https://nvd.nist.gov/vuln/detail/CVE-2026-134842)
* fix: with `standard_conforming_strings` off, the yen sign (`U+00A5`) in a string value now gets a backslash before it, and in simple mode such a value is sent as `E''`. The JDK's EUC_JP and Shift_JIS charsets encode the yen sign as the byte `0x5C`, a backslash for the backend, so with `allowEncodingChanges=true` a value that started with a yen sign and a quote could end the literal and run as SQL. This affects all versions through 42.7.14 [GHSA-6rxc-3r4p-gpff](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-6rxc-3r4p-gpff) [CVE-2026-134842](https://nvd.nist.gov/vuln/detail/CVE-2026-134842)
* fix: the connection is now closed when an unchecked exception interrupts a request, not only an `IOException`. Before, part of a message could stay in the send buffer, and the backend read the next request as the rest of it. A spooled `setBinaryStream()` value executed again after SQLState `0A000` or `26000` could make the bytes of a later uploaded value run as a Query message. In simple mode, a parameter that cannot be rendered is now reported as a failed Bind, and the connection stays usable. This affects all versions through 42.7.14 [GHSA-cww3-qmc2-mjmr](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-cww3-qmc2-mjmr) [CVE-2026-134843](https://nvd.nist.gov/vuln/detail/CVE-2026-134843)
* fix: executing again a statement whose spooled `setBinaryStream()` value was already sent now fails with "Unable to bind parameter values for statement." and the connection stays usable. Before, it threw a `NullPointerException`.
* fix: a fastpath call whose arguments add up to more than `0x3fffffff` bytes now fails with SQLState `22023` before anything is sent. Before, the message length was added up in an `int` and could wrap around, so the backend read the rest of the argument data as new messages.
* fix: `CopyManager` `cancelCopy()` now closes the connection and stops at the second error from the backend. Before, it kept every exception with no limit, so a server, or an attacker on the network path when the server is not verified, could answer a `COPY TO STDOUT` with CopyData messages until the heap was exhausted, or make the loop run forever after the stream closed. This affects all versions through 42.7.14 [GHSA-79c7-9m5j-vqqv](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-79c7-9m5j-vqqv)
* fix: the driver now resolves an unqualified type name, such as `interval` for a `PGInterval` parameter, to the type the server resolves it to, by preferring the type that `pg_type_is_visible()` reports. Before, a domain or type with a built-in name in another schema, even the temporary schema of another session, could be used instead, and the server ran the CHECK of that domain in the application's session. This affects all versions through 42.7.14 [GHSA-j75g-99q3-vr5c](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-j75g-99q3-vr5c) [CVE-2026-134844](https://nvd.nist.gov/vuln/detail/CVE-2026-134844)
* fix: the catalog queries of `PgResultSetMetaData`, `TypeInfoCache` and `PgDatabaseMetaData` now qualify their operators as `OPERATOR(pg_catalog.op)` and their functions with `pg_catalog`. Before, a role that could create objects in a schema of the `search_path` could supply an operator with an exact type match, such as `oid = int4` or `name = varchar`, and have it run with the privileges of whoever called `getTableName()`, `getTables()` and many other methods. This affects all versions through 42.7.14 [GHSA-j75g-99q3-vr5c](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-j75g-99q3-vr5c) [CVE-2026-134844](https://nvd.nist.gov/vuln/detail/CVE-2026-134844)
* fix: an `ssl` value other than `true`, `false` or the empty value, ignoring case, now fails with "Invalid ssl value" and SQLState `08001` when `sslmode` is not set. Before, values such as `1`, `on`, `yes` or `verify-full` silently gave `sslmode=prefer`, so the driver continued without TLS when the peer refused it and accepted any certificate. This affects 9.4.1208 through 42.7.14 [GHSA-3mrw-838h-x9j9](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-3mrw-838h-x9j9) [CVE-2026-134845](https://nvd.nist.gov/vuln/detail/CVE-2026-134845)
* fix: a `service` given in the Properties passed to `getConnection()` is now used when the URL names no service. Before, it was ignored without a warning, including an `sslmode=verify-full` in that `pg_service.conf` entry, and the connection used `sslmode=prefer`. An unknown service in the Properties now fails as it does in the URL. This affects 42.3.2 through 42.7.14 [GHSA-3mrw-838h-x9j9](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-3mrw-838h-x9j9) [CVE-2026-134845](https://nvd.nist.gov/vuln/detail/CVE-2026-134845)
* fix: `BaseDataSource.setUrl()` now replaces every property that the URL has. Before, it set a property only when the DataSource did not have it yet, so a second `setUrl()`, or a setter followed by `setUrl()`, kept an earlier `sslmode`, `channelBinding` or `gssEncMode`, and a later `sslmode=verify-full` was not enforced. Defaults are no longer stored, and `getUrl()` lists only the properties that are set. This affects 42.2.6 through 42.7.14 [GHSA-3mrw-838h-x9j9](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-3mrw-838h-x9j9) [CVE-2026-134845](https://nvd.nist.gov/vuln/detail/CVE-2026-134845)
* fix: `BaseDataSource.getUrl()` now throws `IllegalArgumentException` for a server name with a `/` or `?`. Before, such a name could add URL properties, which take precedence over all others, for example to turn off certificate checks. This affects all versions through 42.7.14 [GHSA-fxh3-3646-629r](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-fxh3-3646-629r)
* fix: an invalid line in `pg_service.conf` is no longer logged whole. A line with an unknown key now logs the key, and a line without `=` logs only its line number. Before, a typo such as `password = secret` printed the password under the default logging setup.
* fix: a startup parameter containing a NUL character is now refused with SQLState `22023`. The StartupMessage is a sequence of NUL terminated strings, so a NUL in the database name, `currentSchema` or `options` ended that value early and turned the rest into further parameters, overriding `user` or `replication`. `%00` in a URL decodes to a NUL. This affects all versions through 42.7.14 [GHSA-36wf-f6m2-v42m](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-36wf-f6m2-v42m) [CVE-2026-134848](https://nvd.nist.gov/vuln/detail/CVE-2026-134848)
* fix: a second AuthenticationSASL request in one connection attempt now fails with SQLState `08P01`, as in libpq. Before, a server, or anyone on the network path when the server is not verified, could start a new SCRAM exchange after each one and make the driver derive the salted password any number of times. This affects 42.7.11 through 42.7.14 [GHSA-52f2-8qjr-7mw4](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-52f2-8qjr-7mw4)
* fix: with `sslNegotiation=direct`, the driver now refuses a peer that did not select the ALPN protocol `postgresql`, with libpq's message. Before, an attacker on the network could send a direct connection to another TLS service with a certificate for the same host, and the driver sent its startup packet there. This affects 42.7.4 through 42.7.14 [GHSA-fpmr-jv7c-hwff](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-fpmr-jv7c-hwff)
* fix: with GSS encryption, every outgoing packet now uses the requested privacy, and a write fails when privacy was requested and not applied. Before, one forged server packet with the sealed flag cleared made every later packet integrity-only, so the SQL and parameter values that followed were sent readable. This affects 42.2.15 through 42.7.14 [GHSA-hcjc-54fp-2p42](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-hcjc-54fp-2p42) [CVE-2026-134846](https://nvd.nist.gov/vuln/detail/CVE-2026-134846)
* fix: with GSS encryption, an incoming packet that is a duplicate, old, out of sequence, after a gap or not encrypted is now refused, and the connection is closed. Before, an attacker on the network path could drop a server reply and deliver an earlier one from the same connection as the answer to the current query. This affects 42.2.15 through 42.7.14 [GHSA-hcjc-54fp-2p42](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-hcjc-54fp-2p42) [CVE-2026-134846](https://nvd.nist.gov/vuln/detail/CVE-2026-134846)
* fix: only the first 32 characters of `server_version` are now parsed, which is enough for three version parts of up to 10 digits each. Before, the driver parsed a version of any length with `java.text.NumberFormat`, which takes time quadratic in the length of a run of digits, so a server, or anyone on the network path under `sslmode=prefer`, could make a connection attempt use minutes of CPU that `loginTimeout` did not interrupt. This affects all versions through 42.7.14 [GHSA-79c7-9m5j-vqqv](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-79c7-9m5j-vqqv)
* fix: a `server_version` that parses to 0, such as one the driver does not recognize, is now parsed once per connection. Before, the number was cached with 0 meaning not parsed yet, so `getTypeInfo()`, `getColumns()` and other metadata calls parsed the string again for every row, and a server, or anyone on the network path under `sslmode=prefer`, could keep one call busy for minutes with a long `server_version`. This affects all versions through 42.7.14 [GHSA-79c7-9m5j-vqqv](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-79c7-9m5j-vqqv)
* fix: the `AsciiStringInterner` of column labels and notification channel names now keeps lookups fast when many labels have the same hash. Before, a peer could make `getConnection()` spend minutes of CPU, before authentication under the defaults, with a RowDescription of labels made to collide. The interner is shared by all connections in the JVM. This affects 42.3.1 through 42.7.14 [GHSA-5hpm-qxj5-h4ww](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-5hpm-qxj5-h4ww)
* fix: a text array whose dimensions need more elements than the value holds, such as a deeply nested value with mostly empty sub-arrays, now fails with SQLState `22000`. Before, the driver took each length from the first sub-array and allocated for it, so a value of under 1 KB from a server, or from an attacker on the network path when the server is not verified, could exhaust the heap. This affects all versions through 42.7.14 [GHSA-79c7-9m5j-vqqv](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-79c7-9m5j-vqqv)
* fix: `PSQLWarning` no longer records a stack trace, which reduces the heap kept per server notice from about 880 to about 160 bytes. `getStackTrace()` of a server warning is now empty. The warning chains still have no limit. This affects all versions through 42.7.14 [GHSA-79c7-9m5j-vqqv](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-79c7-9m5j-vqqv)
* fix: the `XMLReader` of the default XML factory now has the same `EntityResolver` as its `DocumentBuilder`. Before, a SAX driver that ignores the apache.org features, such as Woodstox, loaded the external DTD of an `xml` value read with `getSource(SAXSource.class)`, so whoever could store such a value could make the application send a request to a URL of their choice. This affects 42.2.13 through 42.7.14 [GHSA-8f43-r57c-hghq](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-8f43-r57c-hghq)
* fix: a `BigDecimal` whose scale or weight does not fit the binary numeric format is now sent as text, and the server reports the overflow. Before, the weight and scale were cut to 16 bits, so `999999.99e-262144` was stored as `999999.99` and `1e131072` as `0`, and a scale such as in `1e-200000000` kept a thread busy for minutes before anything was sent. This affects 42.3.0 through 42.7.14 [GHSA-cjcw-9r77-4gwm](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-cjcw-9r77-4gwm) [CVE-2026-134847](https://nvd.nist.gov/vuln/detail/CVE-2026-134847)

### Changed
* fix: when `sslmode` is not set, the `ssl` connection property now accepts only `true`, `false` or the empty value, ignoring case. Any other value now makes the connection attempt fail with "Invalid ssl value" and SQLState `08001`, before a connection is opened. Before, values such as `1`, `on`, `yes`, `require`, `verify-full` or `true` with a trailing space were accepted and silently gave `sslmode=prefer`, which neither requires TLS nor checks the server certificate. Unchanged: `true` and the empty value (as in `?ssl` in a URL) still mean `sslmode=verify-full`, `false` and no `ssl` property still mean `sslmode=prefer`, and `ssl` is still ignored when `sslmode` is set. An application that now fails should set `sslmode` to the mode it wants, or use `ssl=true` to require TLS and verify the certificate. This affects 9.4.1208 through 42.7.14 [GHSA-3mrw-838h-x9j9](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-3mrw-838h-x9j9) [CVE-2026-134845](https://nvd.nist.gov/vuln/detail/CVE-2026-134845)
